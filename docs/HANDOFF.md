# Demand Intelligence — Handoff Status Report

_As of 2026-11-10. Repo: <https://github.com/JCHETAN26/demand-intel> (public). Owner: JCHETAN26._

## TL;DR

- **What it is:** an end-to-end demand forecasting system on Walmart M5 (30,490 SKU × store
  series). It produces probabilistic forecasts (7 quantiles per day, 28 days ahead) and turns
  them into replenishment recommendations. It is served through FastAPI and a Next.js app, with
  MLflow promotion gates, Airflow DAGs, Prometheus/Grafana and Terraform for AWS.
- **State:** research and engineering are about 90% done. Every result in `evaluation/` is
  generated by `make evaluate`, and CI on `main` is green as of `e97f66e`.
- **The one thing blocking "done":** LightGBM beats every baseline but failed one promotion gate
  (test bias −5.03% vs a ±5% limit). The registered champion is therefore still
  `seasonal_naive`. The fix (`lgbm_bc`) is pre-registered in **open PR #2** but has **not been
  run yet**.
- **Biggest surprise for a newcomer:** the API does **not** serve the registered champion. It
  serves plain `lgbm` (see [Known issues](#7-known-issues-and-tech-debt), #1).

## 1. Purpose and scope

The project answers ten questions, fixed in advance in [`PROJECT_SPEC.md`](../PROJECT_SPEC.md)
§3. Verdicts are in [`docs/acceptance.md`](acceptance.md).

1. Does the model beat seasonal naive?
2. Does ML beat statistical baselines?
3. Do LSTM/TFT justify their cost?
4. Are the P10/P90 quantiles calibrated?
5. Does a fine-tuned NLP model beat simple baselines on recall text?
6. Do text signals improve forecasts?
7. Does better forecasting reduce inventory cost?
8. Is the pipeline reproducible end to end?
9. Is serving latency acceptable?
10. Can monitoring detect degradation?

**Data sources**

| Source | Use | Notes |
|---|---|---|
| Walmart M5 (Kaggle) | Sales, prices, calendar, 2011–2016 | Needs Kaggle credentials and acceptance of the competition rules. Items are anonymised. |
| Open-Meteo (historical) | Weather per state | Locations in `configs/weather_locations.yaml` |
| openFDA food enforcement | Recall text (≈10k reports) | Maps only to FOODS × state × week |

**Explicitly out of scope:** real inventory data. M5 has no stock, lead times or costs, so all
inventory figures are **scenarios** and are labelled as such.

## 2. Current results

Full verdicts with confidence intervals: [`docs/acceptance.md`](acceptance.md).

| # | Question | Verdict | Key number |
|---|---|---|---|
| 1 | Beats seasonal naive | **yes** | Test WRMSSE 0.640 vs 0.870; Δ −0.30 (CI −0.31 to −0.29), 5/5 folds |
| 2 | ML beats statistical models | **mixed** (verdict says "no") | Wins vs per-class stats model on all series; vs ETS/ARIMA on the 3,000-series panel the CI crosses 0 |
| 3 | Deep learning justified | **no** | TFT is not significantly better and takes 924 s/fold vs 63 s for LightGBM |
| 4 | Quantiles calibrated | **yes** | P10/P90 inside the discrete-count bracket on 5/5 folds |
| 5 | NLP fine-tune beats baselines | **pending** | Human gold test labels not collected |
| 6 | Text improves forecasts | **no** (null result) | Embedding arm Δ +0.004 (worse), 0/5 folds |
| 7 | Better forecasts cut inventory cost | **yes** (simulated) | P3 vs P1: −46% cost; stockout days 3,319 → 919 |
| 8 | Reproducible MLOps | **yes** | Gates, registry and DAGs work; `make evaluate` regenerates everything |
| 9 | Serving latency | **yes** | `/v1/forecast` p95 9.4 ms (SLO 100 ms); `/v1/inventory/recommend` p95 15.6 ms (SLO 150 ms) |
| 10 | Monitoring | **yes** | Forecast, data-drift and NLP checks run; alert rules exist |

**Drivers (ablation, panel, backtest WRMSSE):** sales history only 0.987 → +calendar 0.728 →
+SNAP 0.726 → +price 0.715. Hierarchy and weather add essentially nothing.

## 3. Architecture

```
 M5 · weather · openFDA
        │  ingest (checksums, manifest, Postgres ledger) → validate (Pandera, quarantine)
        ▼
 features (horizon-bucketed: 1–7, 8–14, 15–28 days; leakage-tested)
        │
        ├─ baselines / statsforecast (ETS, ARIMA, Croston, TSB)
        ├─ LightGBM global, Tweedie objective, direct per bucket → point = mean
        │     └─ QuantileMap: empirical quantiles of y given ŷ (ratio quantiles above 3 units/day)
        ├─ LSTM, TFT (plain PyTorch, panel only, CPU)
        └─ NLP: rules → TF-IDF → embeddings → fine-tuned encoder → state × week signals
        ▼
 rolling-origin backtest (5 × 28-day folds + 1 test window) → metrics → paired tests
        ▼
 promotion gates (mlops/registry/gates.py) → MLflow registry → evaluation/registry.json
        ▼
 forecast-batch → data/serving bundle → FastAPI (in-memory store) → Next.js app
        ▼
 Prometheus /metrics → alert rules → Grafana;  Terraform: ECS Fargate, ALB, RDS, S3, ECR, CloudWatch
```

**Stack:** Python 3.11, uv, pandas, Pandera, LightGBM, statsforecast, PyTorch, scikit-learn,
transformers, MLflow, Airflow, FastAPI, Prometheus, Next.js, Terraform, GitHub Actions.
Code quality tooling: ruff, mypy `--strict`, pytest, pre-commit.

## 5. How to run

**Environment.** Development happens in GitHub Codespaces (4 cores / 16 GB; `.devcontainer/`).
A laptop with 8 GB of RAM cannot run the full-population LightGBM backtest.

```bash
make install              # uv sync --group dev + pre-commit
make check                # ruff + mypy + unit tests (what CI runs)
make up                   # Postgres + MLflow + API (docker compose)
cd apps/web && npm install && npm run dev            # :3000, reads NEXT_PUBLIC_API_URL (default :8000)
docker compose --profile monitoring up -d            # Prometheus :9090, Grafana :3001
```

**Full reproduction:** `make evaluate` takes hours on 4 cores. It needs `KAGGLE_USERNAME` and
`KAGGLE_KEY` (set as Codespaces secrets). `make report` rebuilds the tables and acceptance report
from existing runs in minutes, but some of its steps need `data/` to exist.

**Optional dependency groups** (`pyproject.toml`): `ml`, `deep` (torch), `nlp`, `api`,
`monitoring`, `versioning`. Airflow runs from its own image (`orchestration/airflow/Dockerfile`).

**Environment variables** (`.env.example`): `DI_DATABASE_URL`, `DI_MLFLOW_TRACKING_URI`, and
optionally `DI_S3_BUCKET`. Deploy needs the GitHub secrets `AWS_ROLE_ARN` and `AWS_REGION`.

**Data is not in git.** `data/` is ignored except for `.gitkeep` placeholders. Raw data,
validated data, models and the serving bundle live only where they were generated, which is the
Codespace.

## 7. Known issues and tech debt

Ranked by importance.

1. **Serving vs registry (fixed on branch `fix/serving-champion`).** `forecast-batch` used to
   fall back silently to `lgbm` when the champion (`seasonal_naive`) was not a LightGBM model.
   Selection is now `choose_serving_model()` in `pipelines/inference/serving.py`. A fallback
   logs a warning and is written to `summary.json` (`registry_champion`, `fallback`,
   `fallback_reason`). The API exposes it on `/v1/health`, `/v1/summary` and `/v1/forecast`, and
   the web overview shows a banner. `forecast-batch --strict` fails instead of falling back. The
   fallback itself disappears once a LightGBM model is promoted.
2. **Bias gate failure.** `lgbm` test bias is −5.03% (backtest −4.1%), a systematic
   under-forecast of the Tweedie mean. The fix is pre-registered, not yet run (see §8).
3. **Monitoring report is on `seasonal_naive`.** It shows bias warnings for FOODS (−9.0%),
   HOBBIES (−5.1%) and CA_1. It will need regenerating after any champion change.
4. **NLP question unanswered.** `evaluation/nlp_results.csv` contains only majority, rules and
   TF-IDF rows. Embeddings and encoder results are missing, and the human gold test set has not
   been collected (`demand-intel nlp-import-gold` exists for importing it).
5. **Serving benchmark conditions.** It ran with client and server on one 4-vCPU box, not the
   1 vCPU / 2 GB container named in the spec §11.3.
6. **No live deployment.** The Terraform and deploy workflow exist, but there is no evidence of a
   running environment and no public demo URL.
7. **`acceptance.py` reads the benchmark JSON schema directly.** It broke once when
   `benchmark_api.py` changed format (fixed in PR #1). Consider a shared schema or loader.
8. **Integration tests.** `tests/integration/test_api_e2e.py` (on `fix/serving-champion`) builds
   a real bundle and pins the `/v1/forecast` and `/v1/inventory/recommend` schemas. Ledger and DAG
   tests need Postgres and Airflow.
9. **Starlette deprecation warning** in `fastapi.testclient` (httpx). Harmless for now.

## 8. Work in flight

| Item | State | Next action |

| **PR #2**: pre-register `lgbm_bc` (spec v0.5) | Open, CI green, **not merged** | Merge it **before** running the experiment, so the pre-registration predates the result |
| `lgbm_bc` backtest | Not run | In the Codespace, see the commands below (~1.5 h) |
| Promotion of `lgbm_bc` | Blocked on the run | `promote --challenger lgbm_bc --population full` |

`lgbm_bc` is plain LightGBM plus one change: a per-category factor Σy/Σŷ, learned on each fold's
28-day pre-origin calibration window and clipped to ±10%. It scales the point forecast only.
The gates are unchanged, and `bias_clip` must not be tuned after seeing the result; spec v0.5
says so explicitly. If it fails, the champion stays and the result is reported.

```bash
# In the Codespace, after merging PR #2
git checkout main && git pull
uv sync --group dev --extra ml --extra api
uv run demand-intel ingest m5 && uv run demand-intel splits    # only if data/ is missing
scripts/run_forecasting.sh lgbm_bc
uv run demand-intel report
uv run demand-intel promote --challenger lgbm_bc --population full
uv run demand-intel forecast-batch      # republish the bundle with the new champion
uv run demand-intel monitor
uv run demand-intel acceptance
```

## 10. Rules of the codebase (read before changing anything)

1. **Never hand-edit generated files.** `evaluation/*`, `docs/acceptance.md` and
   `docs/eda_report.md` come from the CLI. Change the code and regenerate.
2. **Spec changes go in the change log first.** Any change to a metric, split, gate or definition
   gets a dated entry in `PROJECT_SPEC.md` §12 with a reason, *before* the run it affects.
3. **The test window is touched once per model family.** Selection uses the 5 backtest folds
   only. §9.3 has the anti-cherry-picking rules.
4. **Gates are not loosened to pass a model.** Fix the model, and pre-register the fix.
5. **No leakage.** Features only see sales up to the origin, and `tests/unit/test_features_lgbm.py`
   enforces this. Keep known-future and past-only inputs separate (spec §2.2).
6. **Inventory numbers are scenarios.** Keep the "SCENARIO — not observed data" label on anything
   derived from the simulator.
7. **Strict typing.** `mypy --strict` must pass, and optional libraries go in the override list in
   `pyproject.toml`.
